Node.js October 2026 Security Releases

On 21 October 2026 Node.js fixed ten vulnerabilities across every supported release line, four of them rated high. The most serious is a memory corruption bug in Brotli decompression, scored 9.2 Critical, and researchers have since shown it can run code through an ordinary fetch() call. Upgrade to 22.23.4, 24.22.1 or 26.12.1. Node.js 20 and older receive no fix.

ACTIVE

Fixed releases, Docker images, Lambda base images, Elastic Beanstalk and Amazon Linux packages are available. Code execution through the Brotli flaw has been demonstrated.

What to do

This is an upgrade, not a configuration change. Node.js has published no workarounds for any of the ten CVEs.

01

Find every Node.js version you run

Check servers, CI runners, developer machines, base images and serverless runtimes. The command below also prints the bundled OpenSSL, c-ares and Undici versions.
SHELL
COPY
node -p "[process.version, 'openssl ' + process.versions.openssl,
  'c-ares ' + process.versions.ares, 'undici ' + process.versions.undici].join('\n')"
02

Upgrade to the fixed release for your line

22.23.4, 24.22.1 or 26.12.1, or anything later in the same line. See fixed versions.
03

Rebuild container images

The official node images were updated on 21 October. An image built before then keeps the old runtime until you rebuild it on a fresh pull of the base.
SHELL
COPY
docker run --rm node:22 node --version   # expect v22.23.4 or later
docker run --rm node:24 node --version   # expect v24.22.1 or later
docker run --rm node:26 node --version   # expect v26.12.1 or later
04

Rebuild single executables and startup snapshots

A single executable application embeds its own copy of Node.js, so it stays vulnerable until it is rebuilt. If you build startup snapshots, rebuild them too. See CVE-2026-106074.
05

Schedule the move off end-of-life lines

Anything on Node.js 20 or older stays exposed to every issue on this page. Treat it as a known, unfixed vulnerability until it is migrated.

End-of-life lines

The Node.js security post states that end-of-life versions are always affected when a security release occurs. Node.js 20 reached end of life on 30 April 2026 and Node.js 25 on 1 June 2026. The Node.js project recommends that production applications use only Active LTS or Maintenance LTS releases.

Services that are not on the internet

A service nobody can reach from outside still calls out: to AI, payment, CRM and data providers, and to your other services. Several of these fixes protect those outbound calls, so not being internet-facing does not mean not affected. It usually does mean not urgent.

For most of these, an attacker has to control a service you call or get onto the network path between you and it. From inside a private cloud network that is hard, which is why most internal services can take this on a normal rebuild cycle. The exceptions are services that accept Brotli request bodies, and services that call or connect to addresses users supply, such as webhook senders.

This table is our reading of the fix commits and the “Who is exposed” notes below, not guidance from Node.js. A WAF, CDN or load balancer in front of a service only sees traffic coming in. It plays no part in the calls your service makes out.

HIGH
CVE-2026-111497: Brotli decoder out-of-bounds write

Affects 22.x, 24.x and 26.x. Fix: Node.js commit, google/brotli commit

The bug is in the Brotli library that Node.js bundles, not in Node.js’s own code. A crafted compressed stream that declares a single block type and then switches blocks was not rejected, and Node.js says the result is an out-of-bounds write that permits remote code execution. Node.js applied the upstream fix, which makes the decoder stop with an error on such streams.

Code execution has been demonstrated. On 22 October Imperva ran code on the official Node.js 24.22.0 image through both a Brotli response read by the built-in fetch and a Brotli request body handled by Express and body-parser, and confirmed 24.22.1 rejects the same input. The CVE record, published by Google, scores it 9.2 Critical under CVSS 4.0 and covers Google Brotli 1.0.3 to 1.2.0, so other software that bundles Brotli needs its own update. No attacks had been reported as of 25 October, and it was not in the CISA KEV catalog.

Who is exposed: anything that decompresses Brotli data it does not control. zlib.brotliDecompress, its sync form and zlib.createBrotliDecompress all reach the decoder; the fix’s regression test exercises both the one-shot and streaming paths. Typical cases are servers that accept Content-Encoding: br request bodies and clients or proxies that decompress responses from servers they do not trust.

The built-in fetch reaches it. For HTTPS URLs it asks servers for Brotli by default (Accept-Encoding: br, gzip, deflate) and decodes Brotli responses with Node.js’s own zlib, in the bundled Undici of all three fixed releases. Any fetch call to a server that is malicious or has been compromised can deliver a crafted response. This is our reading of the source; Node.js has not said it.

HIGH
CVE-2026-105482: DNS resolve truncates names at a NUL character

Affects 22.x, 24.x and 26.x. Fix: Node.js commit

The DNS resolver hands names to c-ares as C strings, which end at the first NUL character. A name such as example.com\0.trusted.corp passes a JavaScript check like endsWith(".trusted.corp"), but the query actually goes out for example.com. The fix commit uses this example.

Who is exposed: applications that pass user-supplied names to dns.resolve, any resolve* method, dns.reverse or a Resolver instance after checking them as strings, for example to enforce an allowlist. After the fix these calls throw ERR_INVALID_ARG_VALUE for names containing a NUL. The change does not touch dns.lookup.

HIGH
CVE-2026-106069: TLS hostname bypass with non-canonical IP addresses

Affects 22.x, 24.x and 26.x. Fix: Node.js commit

Before checking a server’s certificate, Node.js normalised the hostname. Strings such as 0127.0.0.1, 0x7f.0.0.1 or 127.1 could be checked against the certificate as one address while the operating system’s resolver connected to another. According to the CVE record, the certificate check reads 0127.0.0.1 as octal, 87.0.0.1, while the operating system’s resolver on some platforms, such as macOS, reads it as decimal and connects to 127.0.0.1. A server at the connected address can then present a certificate issued for the other address.

Who is exposed: applications that open TLS connections to host strings an attacker can influence, such as webhook senders, URL previewers and proxies. Based on the fix’s tests, the attacker also needs a certificate the client trusts whose DNS name is the IP address written normally. Connections to fixed, ordinary hostnames are not affected. After the fix, tls.checkServerIdentity rejects these hosts with ERR_TLS_CERT_ALTNAME_INVALID.

HIGH
CVE-2026-105483: TLS hostname bypass with fullwidth digits

Affects 24.x and 26.x. Fix: Node.js commit

A related regression in the same hostname check. A host written with fullwidth digits, such as １２７.0.0.1, was normalised into an ordinary IP address and could then match a certificate issued for that address. The fix rejects any host that only becomes an IP address after normalisation. Node.js 22 does not have the regression.

Node.js rates this high, but the fix commit itself describes it as a low-severity bug that is not easy to exploit. We show the rating from the security release post.

MEDIUM
CVE-2026-106072: DNS names in certificates accepted for IP endpoints

Affects 22.x, 24.x and 26.x. Fix: Same commit as CVE-2026-106069

A second report of the same underlying problem, fixed by the same change. A certificate whose DNS name reads 127.0.0.1 could authenticate a connection made to a non-canonical form of the address, such as 0177.0.0.1. Upgrading for CVE-2026-106069 fixes this too.

MEDIUM
CVE-2026-105481: Keep-alive socket accepts a response sent too early

Affects 22.x, 24.x and 26.x. Fix: Node.js commit

When the HTTP client reuses a kept-alive connection, a server could write a response onto the idle socket before the next request was sent, and Node.js would treat it as the answer to that request. An earlier guard only caught this when the event loop had polled the socket. The fix asks the operating system whether unread data is waiting before reusing a socket, and opens a new connection if it is.

Who is exposed: clients using an http.Agent with keepAlive enabled that talk to a server which is malicious or compromised, or to a plain HTTP server through an attacker on the network path.

MEDIUM
CVE-2026-106074: Repeated random values in snapshots and SEAs

Affects 22.x, 24.x and 26.x. Fix: Node.js commit

crypto.randomUUID() and crypto.randomInt() keep a small cache of random values. When an application built a startup snapshot, the unused part of that cache was saved into it, so every process started from the snapshot produced the same first values. The fix clears the caches when a snapshot is written and when it is loaded.

Who is exposed: only applications built as single executable applications with useSnapshot enabled, or that use user-land startup snapshots. Ordinary applications are not. Node.js has not published rotation guidance; our recommendation is to rebuild affected binaries on a fixed version and to treat any UUIDs or random numbers they used as secrets, such as tokens or nonces, as predictable and rotate them.

LOW
CVE-2026-106070: ZipFile returns stray bytes after a failed header check

Affects 26.x. Fix: Node.js commit

zlib.ZipFile is an experimental API added in 26.8.0 for reading ZIP archives. When a ZIP entry failed header validation, a later read of that entry could return bytes from the wrong position in the file. Only 26.x has this API.

LOW
CVE-2026-106071: Permission Model over-grants with wildcard paths

Affects 26.x. Fix: Node.js commit

With the Permission Model enabled, a wildcard path in --allow-fs-read or --allow-fs-write could grant access to more paths than it should. According to the CVE record, a path shorter than a wildcard rule’s prefix could be treated as matching it.

LOW
CVE-2026-106073: Permission Model bypass through fs.realpathSync

Affects 22.x, 24.x and 26.x. Fix: Node.js commit

fs.realpathSync() skipped the Permission Model check that its siblings, such as fs.promises.realpath() and fs.existsSync(), already performed, so it could be used on paths the process had not been granted.

On both Permission Model issues: the Node.js documentation describes the Permission Model as a seat belt that stops trusted code from accidentally touching files it was not granted, and states that it does not protect against malicious code. Do not rely on it to contain untrusted code, patched or not.

Published since 21 October

CVE records and scores. All ten records were published on 22 and 23 October with CVSS scores, now in the table above. Node.js also added a summary for each CVE to its security release post.
