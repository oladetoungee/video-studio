01 / 07
First, ask
the database

You added an index on email. Put EXPLAIN in front of the slow query.

PostgreSQL
EXPLAIN SELECT * FROM users
WHERE email = 'bob@email.com';
two possible outcomes
bad: Seq Scan on users
good: Index Scan using idx_users_email
Seq Scan = every row read.
Index Scan or Bitmap Index Scan = index used.
MySQL: ALL = full scan; ref/range = index.
02 / 07
Mistake 1:
a function on
the column

The index stores emails as they are.

PostgreSQL, index on users (email)
WHERE LOWER(email) = 'bob@email.com'
Seq Scan on users
fix: index the same expression
CREATE INDEX idx_users_lower_email
ON users (LOWER(email));
Index Scan
MySQL's default collation ignores case, so LOWER() is rarely needed.
03 / 07
Mistake 2:
a wildcard
at the start
WHERE title LIKE '%fall%'
Seq Scan
fix: a trigram index
CREATE EXTENSION IF NOT EXISTS pg_trgm;
CREATE INDEX idx_title_trgm ON posts
USING gin (title gin_trgm_ops);
Bitmap Index Scan
Prefix only ('fall%')? A B-tree with text_pattern_ops works.
04 / 07
The index Postgres
never made for you

MySQL (InnoDB) creates an index on a foreign key column for you. PostgreSQL doesn't.

PostgreSQL
CREATE INDEX idx_orders_customer_id
ON orders (customer_id);
Laravel
$table->foreignId('customer_id')
->index()->constrained();
Live table? Add CONCURRENTLY (no write lock).

A common reason joins suddenly get slow after a move to Postgres.

05 / 07
When to add
an index
01
Searched often
In WHERE, JOIN or ORDER BY.
02
EXPLAIN shows a full scan
On a query that is slow.
✗
Not on every column
A table with 6 indexes: 1 row + 6 indexes = 7 writes per insert.
✗
Not on tiny tables
With about 10 rows, the database scans anyway.

Every index speeds up some reads and slows down every insert.
