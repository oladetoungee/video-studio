## What she says (approx. times on the raw file)
- **0:20 Open.** As you get more users, your database grows and your tables get bigger; your app takes longer to load, performance issues. "One thing that you can always use to fix this is a database index." Agenda: no index, what an index is, how it finds things fast, types, mistakes.
- **0:46 Without an index.** A bookstore, the books table has a million rows, "we run this query" (code on screen: `SELECT * FROM books WHERE author_id = 42;`). The database has no idea where author 42's books are; it starts at the first row and checks every single row, all one million: a **full table scan**. "In many cases it can be very problematic." At "10, 100 rows" you wouldn't notice; at a million rows it's a problem.
- **1:28 What a database index is.** The index at the back of a book: sorted alphabetically, gives you the page number. A separate structure that stores the values from a column in sorted order, with a pointer to where each row lives; it only stores the column and the pointer, so it is "way much more smaller" than the table.
- **2:03 How it finds things fast.** She read an article, loves the writer's explanation, uses its example, will link it in the description. Index on email, looking for bob@email.com: opens in the middle, sees dave → Bob comes before Dave, move left → alice → Bob comes after Alice, move right → keeps going until bob@email.com; Bob's entry has a pointer to Bob's row. "Even with a million rows… in about 20 steps or so." Without an index up to a million checks in the worst case. (She says "Without an index, you will do way less than that" at 2:52: a slip for **"With an index"**.)
- **2:54 B-tree.** Most databases store indexes in a B-tree; it works like the article's example; millions of rows, only a few levels.
- **3:10 How to add one.** "Adding a database index will literally up your query optimisation game", a one-liner; SQL (`CREATE INDEX …`), Laravel migration (`$table->index('author_id')`). Then the database goes to the index first, finds author 42, goes straight to those rows.
- **3:31 Check it is used.** Put EXPLAIN in front of your query. PostgreSQL: Seq Scan = reading every row; Index Scan = using your index. MySQL: a small table; "all" = full table scan; "ref or range" = using an index. "If a query is slow… confirm: is this query doing a full scan or is it using an index?"
- **4:11 Types.** People talk about B-tree, hash, bitmap "and many like that"; she focuses on three.
  - **4:22 B-tree**: the default when you don't name a type; exact matches (user with this email), ranges (books priced between 10 and 15 [listen: kit says 50]), sorting (newest orders first), "how they start" (titles that start with "Harry" [whisper: "Ari"; kit: "Harry"; listen]), works because the index is sorted.
  - **4:51 Unique**: no two rows with the same value, no two users with the same email; "your primary key already has one".
  - **5:04 Composite**: "this one kind of always confuses me". Index on last name + first name in that order: helps last name, helps last name + first name, usually not first name only. **Phone book** (5:22-6:07): sorted by surname, all the Adeyemis together, all the Okafors together, first names sorted inside each surname, Ada Okafor before Chidi Okafor; finding Ada Okafor is easy; everyone named Ada is spread out (Ada Adeyemi at the front, Ada Okafor in the middle, Ada Williams near the end), you'd have to read every page. Tip (6:07): put the column you search by most often first.
  - **6:15 The rest**: hash (exact matches only, a login session by its exact token; no ranges or sorting, so most people use B-tree); bitmap (columns with few values, a status column: active, inactive, banned; mostly in databases built for reports); spatial (location data, coffee shops/restaurants, a ride app finding drivers near you; groups places that are near each other on the map, so the app only checks places around you); full-text (searching inside text, an online store search for "wireless headphones"; indexes each word). Covering and partial: **named only, not explained**.
- **7:20 Clustered vs non-clustered.** Clustered decides the order the table's rows are stored in (phone book: the data itself is sorted by surname; find the name, you found everything); only one per table. Non-clustered: separate structure pointing back to the row (index at the back of a book); a table can have lots.
- **7:55 The cost.** "If database indexes make queries so fast, why don't we just index every column?" Every insert, update, delete also updates every index; orders table with six indexes = the table plus six indexes on every new order; slower writes; storage; for a small table (about 10 rows) the database often skips the index and scans anyway. Index only the columns you search, filter, join or sort by. "As good as it is, it can also get costly too."
- **8:48 Mistakes that stop an index working.** (1, 8:59) Wrapping the column in a function (`LOWER(email)`): the index holds emails as stored, the lowercase versions are not in it, so the database can't use it, unless you create an index on the same expression. (2, 9:17) A wildcard at the start of a LIKE: the index is sorted by how values start; if you don't know how it starts, the index can't help.
- **9:29 Foreign key gotcha.** MySQL creates an index on a foreign key column automatically (if none exists); PostgreSQL doesn't; if you're on Postgres or moved from MySQL, check your foreign key columns have indexes; a common reason joins suddenly get slow.
- **9:53 When to use one.** A column that keeps showing up in WHERE, joins, ORDER BY. A million orders sorted by date, show the first 10: without an index, look at a million rows and sort them; with one, read them in order and stop after 10. When EXPLAIN shows a full scan on a slow query. When a table is read a lot more than written. Not when the table is small, or written constantly but rarely searched.
- **10:53 End.** "So that's it with database indexes. Bye."

## Verified facts (checked 2026-10-12; sources in `kit/refined-kit.md` section 9)
- **Full table scan**: correct. PostgreSQL calls it Seq Scan; MySQL EXPLAIN shows `type: ALL`.
- **Index = sorted copy of a column + pointer to the row**: correct as a simplification. "Much smaller than the table": usually true for a narrow column; a wide or multi-column index can be large. Keep "usually smaller" on screen.
- **"About 20 steps" for a million rows**: correct for the bob/dave/alice halving picture (2^20 = 1,048,576). A real B-tree node holds hundreds of keys, so it is really **3-4 page reads**, with ~20 comparisons spread across them. Her "only a few levels" is right. On screen: "about 20 comparisons" or "a few levels", never "20 disk reads".
- **"One thing you can always use to fix this"**: SIMPLIFIED. An index fixes slow lookups; apps also get slow from N+1 queries, fetching too much, no caching, etc. Never write "fixes every slow app" in titles or captions.
- **Most databases use B-trees** (strictly B+trees): PostgreSQL, MySQL InnoDB, SQL Server, Oracle, SQLite. Correct. B-tree is the default `CREATE INDEX` type in PostgreSQL and MySQL. Correct.
- **B-tree "starts with"**: correct for `LIKE 'Harry%'`. Caveat: in PostgreSQL with a non-C collation, a prefix LIKE needs an index built with `text_pattern_ops`. Not needed on screen.
- **Unique**: correct; a primary key automatically gets a unique index in PostgreSQL and MySQL.
- **Composite / leftmost column**: correct, and her "usually" is right: PostgreSQL 18 (Sept 2025) added **skip scan**, and MySQL 8.0.13 has a skip-scan range method, so a composite index can sometimes help a query on the second column (mainly when the first column has few distinct values). Keep "usually".
- **Hash**: exact matches only, no ranges or sorting: correct (PostgreSQL hash indexes are crash-safe since v10; MySQL InnoDB does not let you create hash indexes).
- **Bitmap**: correct for Oracle and data-warehouse databases. **PostgreSQL and MySQL have no bitmap index you can create** (PostgreSQL builds bitmaps on the fly during a query). Fine as she says it ("databases built for reports").
- **Spatial**: correct (R-tree / GiST, PostGIS). Her "when you search restaurant name, a coffee shop name" is loose: the spatial index serves the **near me / location** part, not the name. On screen: "coffee shops near me".
- **Full-text**: correct (an inverted index of words: PostgreSQL GIN on tsvector, MySQL FULLTEXT).
- **Covering / partial**: exist. Partial: PostgreSQL yes, MySQL no (SQL Server calls it "filtered").
- **Clustered**: correct for MySQL InnoDB (the primary key is the clustered index) and SQL Server. **PostgreSQL has no maintained clustered index** (its `CLUSTER` command sorts once and is not kept up). Add "in MySQL and SQL Server" if it goes on screen.
- **Write cost, storage cost, small tables skipped by the planner**: correct.
- **Function on the column**: correct; fix = expression index (PostgreSQL) / functional index (MySQL 8.0.13+). (In MySQL the default collation is case-insensitive, so `LOWER()` is often unnecessary there.)
- **Leading wildcard**: correct for a normal B-tree. Workarounds exist (PostgreSQL `pg_trgm` trigram index, full-text search); she does not need to mention them.
- **Foreign keys**: correct. MySQL InnoDB requires an index on foreign key columns and creates one if missing; PostgreSQL does not index the referencing column automatically.
- **ORDER BY + LIMIT**: correct; an index in that order lets the database stop after the first rows.
- **EXPLAIN**: EXPLAIN shows the plan without running it; EXPLAIN ANALYZE (PostgreSQL) runs it and shows real times. MySQL `type`: ALL = full table scan; ref / range / eq_ref / const = index used; careful: `type: index` means it scans the **whole index**, which is also slow.
- **The article**: Sergey Egorenkov, "How Database Indexes Work (In Simple Words)", Medium (per her kit; Medium blocked our fetch, so the date and example are taken from the kit). Credit it whenever the bob/dave/alice walkthrough appears.
