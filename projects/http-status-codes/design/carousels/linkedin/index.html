Is your API returning the right HTTP status code?

The codes I use in real APIs, and the mistakes I see most.

01 / 10
Your front end and your monitoring read the status code first
HTTP/1.1 200status code OKreason phrase

The code tells them what happened, and the body gives the detail. If the code is wrong, everything that reads it is wrong too.

02 / 10
The first digit tells you which class it is
1xx
Informational, you rarely see these
2xx
Success
3xx
Redirection
4xx
Client error, check the request
5xx
Server error, check the server
03 / 10
200 isn't the only success
200
GET /books/42
OK, with the book in the body
201
POST /books
Created, usually with a Location header
204
DELETE /books/42
No Content, an empty body
04 / 10
Which redirect? 301, 302, 307 or 308
Permanent
Temporary
May switch POST to GET
301Moved for good
302Back soon
Keeps POST as POST
308Moved for good
307Back soon

With 301 and 302 a POST can turn into a GET, and the data you sent is dropped. If POST requests matter, I would use 307 and 308.

05 / 10
400 or 422?
400
Bad Request
The server can't read the request, like broken JSON
422
Unprocessable Content
The JSON is valid. The data inside makes no sense

I think 422 is clearer for validation, because it tells the front end that the format was fine and the data is what needs fixing.

06 / 10
401 and 403 lead to different screens
401
Expired token
Send the user to log in or refresh their token
403
Not allowed
Show a message that they don't have access

If you return 403 for an expired token, your front end never sends the user back to log in, and they are just stuck.

07 / 10
GitHub hides private repos behind a 404
GitHub Docs, Troubleshooting the REST API

RFC 9110 allows this too, as a way to avoid confirming that private resources exist.

08 / 10
Your app sends 500. The proxy sends 502 and 504
500
Internal Server Error
Usually an uncaught exception
502
Bad Gateway
The proxy got an invalid answer from your app
504
Gateway Timeout
Your app took too long, like a slow query
